## 四人分工目录

P1 已交付目录保留旧分工作为历史记录。P2 及后续新任务使用：

- `UI`
- `场景`
- `玩法功能`
- `审核测试与优化`

UI、场景、玩法功能在共享契约冻结后并行开发，只能依赖契约与各自替身，不能把另外两条实现轨道列为开工前置。审核测试与优化负责人不领取 task 编号，按阶段审核清单维护契约、独立验收、集成门禁和优化，不建立第二套生产玩法。

## 各产品阶段审核重点

| 产品阶段 | 审核重点 |
|---|---|
| P1 | 100m 单发、3 发/轮与 3 轮评级；任务说明/实射/分析/下一轮/评级 UI；枪械拾取、双手门禁、无 VR 替身；100m 场景尺度、命中表面、Console、VR 舒适度和性能。P1 已完成，后续作为回归基线。 |
| P2 | 固定卧姿和无人工移动；拾枪后 UI 显隐；移动靶速度、倒计时、40m 路线、左端禁射；快速扣动两发、长按连射、逐发弹药/命中、P1 单发回归；移动靶 UI、场景独立性、无 VR/VR 闭环和性能。详见 [P2 分阶段审核清单](阶段二-P2-移动靶闭环/阶段审核清单.md)。 |
| P3 | 堑壕/城镇范围与 BDD；敌人/队友/血量/搜索状态机；固定随机种子、NavMesh 与生成点；HUD/小地图不得计算 AI 规则；战斗场景遮挡、队友路径、无 VR 回归、VR 舒适度和性能。P3 任务冻结时再补详细审核节点。 |

每个产品阶段都按“开发前契约 → 分线实现 → 候选集成 → 阶段收口”四个节点审核，但这些节点不使用 `task*.md`，也不计入生产任务完成率。

## 文件命名

- UI、场景、玩法功能三个生产负责人目录必须有 `任务清单.md`；审核测试与优化使用阶段审核清单，不建立 `task*.md`。
- 具体任务规格文件使用 `task001-任务简称.md` 格式。
- 任务编号在同一阶段内全局唯一，避免不同负责人目录出现重复编号。
- 任务规格必须写明 BDD 引用、接口文档引用、交付物、测试要求和联调对象。
